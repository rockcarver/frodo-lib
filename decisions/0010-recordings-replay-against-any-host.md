# Recorded HTTP traffic replays against any host, and the framework is a library feature

## Context and problem statement

Contributors record against their own environment, and everyone else must be able to replay those recordings. frodo-cli runs its whole end-to-end suite this way, and any tool built on frodo-lib can use the same mechanism. `RECORD_REPLAY.md` documents it and calls the matching rule "a design decision, not a shortcut". Recorded retroactively and checked against the code on `main` (42632f3cd, 2026-10-24).

## Decision

- Replay matches a request on method, URL pathname, query and hash, request body (except on the login routes) and order. It ignores host, port, protocol, credentials in the URL and all headers.
- Therefore nothing keys a recording name, cassette or matcher by hostname. Recording names contain no hostname; hosts only decide how traffic is routed into per-area recordings (`FRODO_MOCK_HOSTS`).
- The login sequence is recorded once per deployment type (`cloud`, `forgeops`, `classic`) in a shared cassette, chosen by `FRODO_MOCK_DEPLOYMENT`. An ordinary recording run does its login live and does not write the cassette; refreshing it is deliberate (`FRODO_MOCK_REFRESH_SHARED_AUTH=1`), and a run that needs its own login opts out (`FRODO_MOCK_DEDICATED_AUTH`).
- Secrets are masked when a recording is written (`filterRecording()` in `PollyUtils.ts`). That is a denylist, so the diff of a recording is reviewed before it is committed, and nobody records against an environment holding data that cannot be published.
- A recording older than 90 days produces a warning on replay, never a failure (`FRODO_MOCK_EXPIRES_IN`, `FRODO_MOCK_EXPIRY_STRATEGY` change this). Recordings are never pruned automatically; stale ones are removed by hand.
- Directory names are generated by Polly and are never hand-written. An invocation sets `FRODO_TEST_NAME` explicitly.
- The mechanism is process-wide and configured only through environment variables. It is a library feature for tools that run frodo-lib, including frodo-cli's tests. `setupPollyForFrodoLib` and its helpers are not part of the public API; a change to the framework goes into frodo-lib, and `RECORD_REPLAY.md` is updated in the same pull request.

## Consequences

- A recording made against one tenant replays against any other. The cost: a recording can hide a host-specific behaviour, and the shared login cassette is order-indexed, so overwriting an entry during an unrelated run can break every other run.
- The framework knows the names of the frodo-cli binary (`frodo`, `frodo.exe`, `app.cjs`) and reads `process.argv` to derive recording names, and it prints status lines with `console.log`. This is the documented exception to the "library is free of interface-specific code" rule; it is test tooling, not part of the facade.
- Measured: no recording directory in frodo-lib (`src/test/mock-recordings`) or frodo-cli (`test/e2e/mocks`) has a name that contains a tenant hostname.
- Replacing Polly is deferred (umbrella record 0014): the record-mode harness (per-host routing, shared login cassette, 28 routing directives) is coupled to it.
